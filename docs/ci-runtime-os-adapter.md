# Hermes CI Runtime OS adapter

The advisory adapter pins NeoEngine policy `2.1.0` from `871e416afc55db187d2b6f29c9ff7cac96472223` through `ci/runtime-os/policy-bundle.lock.json`.

Trusted-base code selects affected isolated tests, including direct-import and monkeypatch consumers, and fails closed to all six slices plus e2e for broad or unknown executable changes. A full-proof plan that selects zero unit test files, or any test path containing `:` (the matrix separator), fails the plan instead of passing with e2e alone or running decoy paths. The canonical decision-contract digests and Hermes repository profile are locked with historical parity fixtures. `merge_group` always receives full proof.

## Privilege split

`ci-runtime-os-advisory.yml` executes base-branch code only when triggered by `pull_request_target`, and only for PRs into the protected `main` branch (`branches: [main]`; `pull_request_review`, which cannot be branch-filtered, is held to the same rule by `preflight`'s `base.ref == default_branch` guard), so `base.sha` is protected history whenever trusted code from it is checked out and run (`review-evidence`, which runs under `always()`, only checks out its validator after `preflight` admitted the event). It never checks out or runs the PR head: it fetches the head as inert git objects into the trusted checkout for `git diff --no-renames --name-only` (rename detection off, so a renamed source path is still classified), classifies risk from that list plus the PR body, and evaluates review evidence and admission from the GitHub API. `preflight` (self-hosted) discards workspace residue before checking out trusted code. `Hermes CI required`, `Review evidence required`, and `Merge admission` run on GitHub-hosted runners: they run under `always()` even for fork PRs, so they never touch the self-hosted pool, and they fail closed because `preflight` did not succeed. The push/merge-group/schedule/dispatch proof jobs check out the event's own ref (never a PR head under `pull_request_target`; on `merge_group` that is the queued merge commit, whose workflow definition GitHub also loads from that ref, and review/admission fail `merge_group` closed) and rely on `actions/checkout` cleaning the repository directory. `tests/ci/test_pull_request_target_safety.py` is a fail-closed regression guard over workflow text, not a proof of shell or interpreter semantics. Its aim is that only trusted content enters the privileged workspace. In every `pull_request_target` workflow:

- checkout `ref` must be one of an exact allowlist of base refs, and `repository` absent or `${{ github.repository }}`; `github.sha`-style refs (which resolve to the PR merge ref on `pull_request_review`) require the non-PR-event guard;
- action inputs may not carry PR-head refs directly, through `env`, or via bracket indexing;
- every shell `run:` uses the default/bash shell, may invoke git (by name or path, without `-c` overrides) only as allowlisted plumbing (`fetch`, `cat-file -e`, `diff --name-only`/`--name-status`, `ls-files`, `rev-parse`, `status --porcelain=v1 --untracked-files=all`, each with allowlisted options), and may download only with a `sha256sum -c` pin in the same step;
- step actions come from a fixed allowlist, `download-artifact` is same-run only, and `github-script` may neither spawn processes nor fetch repository content;
- local reusable workflows and composite actions are scanned recursively, and remote reusable workflows are rejected;
- `pull_request_target` must be limited to `branches: [main]` when the workflow checks out code; jobs may not declare `container`/`services`; every remote action is pinned to a full commit SHA; `actions/cache/save` needs a push-only or non-PR guard; `run`/`shell`/`github-script` bodies may not interpolate `${{ }}` expressions (pass values through `env`) or pipe output into an interpreter, and may not download artifacts or repositories from other runs or install packages from URLs; downloads must carry a `sha256sum -c` pin naming the downloaded file; action inputs may use event payload fields only for the exact base refs and repository metadata; loader-style environment variables (`BASH_ENV`, `GIT_*`, `NODE_OPTIONS`, `LD_*`, …) and command substitution in `env` values are rejected; `setup-uv` must set `enable-cache: false`; `github-script` may not load workspace files or download artifacts.

Privileged scripts run with `python3 -I -X pycache_prefix=<fresh per-job dir>`: isolated mode keeps a new module beside a pinned script from shadowing a standard-library import, and the bytecode prefix keeps a committed `__pycache__/*.pyc` from running in place of a pinned source; a test also fails if any bytecode is tracked. The scanner flags literal `python…` invocations of `.runtime-os-*/` or `trusted/` scripts that lack these flags (other invocation shapes rely on the file pin), and behavioural tests plant both a shadow module and an unchecked-hash `.pyc`. The review tripwire is `tests/ci/pull_request_target_reviewed_files.json`: it pins the SHA-256 of the exact bytes of every `pull_request_target` workflow, every local reusable workflow and composite action (with its directory) it reaches, and the scripts the advisory executes from its trusted checkouts (`scripts/ci/runtime_os_adapter.py`, `scripts/ci_risk_classifier.py`, `scripts/ci_risk_classifier_core.py`, `scripts/review_receipt_validator.py`). Any edit to such a file (bodies, `env`, `if`, `with`, triggers, jobs) and any new `pull_request_target` workflow fails the test until it is re-pinned, which forces a visible, reviewable change to the pin file. It is a tripwire, not an authority boundary: a PR can update the pin in the same change, and no CODEOWNERS rule binds the pin file today. Scope is `pull_request_target` only (not `workflow_run` or `issue_comment`). The pattern rules above are defence in depth that explain why a change is risky. Knowingly tolerated violations must be listed by exact text in the test and fail as stale once fixed; the list is currently empty.

Commands assembled at run time (`python -c`, `eval`) are outside what it can see.

PR-head execution (environment build, test slices, e2e) runs in `ci-runtime-os-candidate.yml` on `pull_request`, on GitHub-hosted ephemeral runners, under the same job names. The `Await unprivileged candidate proof` job (GitHub-hosted, `actions: read`; it holds one hosted job slot while polling with backoff from 30 seconds to 5 minutes and retries rate limits (429, or 403 with rate-limit headers or message), server-side, and network API failures; other client errors, including permission 403s, fail fast) binds `Hermes CI required` to the latest same-repository candidate run associated with exactly this PR, for the exact head SHA and base SHA (stamped into the candidate `run-name` when the run is triggered), and fails closed when the PR's own commits (merge-base diff) modify the candidate workflow or when no run appears within 20 minutes. The definition guard only covers the PR's own commits against `main`; a writer who retargets a PR to a branch they control and back, or opens a sibling PR from the same head branch into such a branch, can produce a candidate run from that branch's definition that the waiter accepts, which is within the writer-controlled non-claim below. The tests, runner, and test configuration under proof are themselves PR content (see below). Candidate slices check the restored checkout is clean (`git status --porcelain=v1 --untracked-files=all`, the receipt validator's query) before any candidate code is imported, then run `scripts/run_tests_parallel.py` directly in the prebuilt environment, as `tests.yml`'s required slices do, additionally pinning `TZ`/`LANG`/`LC_ALL`/`PYTHONHASHSEED` (the bootstrap wrapper's `env -i` clean environment is not reproduced; `tests/conftest.py` pins the same values per test). The cleanliness check uses `/usr/bin/git`; the environment build has already run the candidate's build backend and `.gitignore` is candidate content, so this is a check on the restored artifact layout, not a trust boundary; e2e runs `tests/e2e/` exactly as `tests.yml` does (`integration`-marked tests need external services and stay deselected by the repository addopts).

Boundaries this split does not claim:

- The preflight's head fetch runs with `persist-credentials: false`, so it relies on this repository being public (an anonymous `git fetch origin <head-sha>` of a same-repository PR head, verified 2026-10-01). A private copy would need an authenticated, read-only fetch.
- The self-hosted advisory jobs (`preflight` and the push/merge-group proof) need a runner group that admits this public repository. Until one does, they stay queued and the privileged path (inert fetch, definition guard, waiter) has not run live; only the candidate half is proven by live runs.
- `pull_request` and `pull_request_review` runs load workflow files from the PR merge ref. A repository writer can edit either workflow on their branch, so the candidate workflow's read-only permissions and the advisory verdict on review events are only as trustworthy as that writer, which matches the access they already have through any pushed-branch workflow.
- `Hermes CI required`, `Review evidence required`, and `Merge admission` run on GitHub-hosted runners for every event, and PR-event proof also depends on hosted candidate jobs and the waiter; a hosted-runner outage or billing denial turns them red with no self-hosted fallback. Many concurrent PRs can queue behind each other's waiters on the hosted concurrency limit.
- Candidate tests remain PR-controlled code: a PR can change tests, `scripts/run_tests_parallel.py`, `pyproject.toml` addopts, `tests/conftest.py`, or `.gitignore`, exactly as it can for `tests.yml`. The result is evidence about the candidate, never policy, review, or admission authority.
- The candidate jobs reuse the advisory's check names (`Runtime OS slice N/6`, `Runtime OS e2e`, `Build immutable ci-fast environment once`), so each appears twice on a PR: green from the writer-editable candidate workflow and skipped from the advisory. None is a required context; a ruleset or other consumer must bind to the workflow path or check-run app and run, never to these names (the same applies to `Hermes CI required`, which a writer-defined workflow can also emit).
- The base-defined candidate workflow no longer runs PR-head code on the shared, persistent self-hosted `qwen-ops` host. A writer or fork that edits workflow files can still target self-hosted labels; that exposure is governed by runner-group repository access and fork-approval settings, not by this workflow. Workspace cleanup in `preflight` is not host-level isolation: host state such as a runner user's git configuration is outside this workflow's control.

Open PRs that predate the candidate workflow, label- or body-only events on a head with no candidate run, PRs whose head is shared with another open PR (never bindable), and PRs whose base advanced or was retargeted after their last candidate run need a push, branch update, or reopen to create a matching run. After re-running a failed candidate run, re-run the advisory workflow (or push, label, or review) to refresh `Hermes CI required`. Push, merge-group, schedule, and dispatch events still run the proof inline from trusted refs.

One run-scoped immutable `ci-fast` artifact contains the locked Python environment and pinned ripgrep binary; selected slices restore it instead of repeating downloads and dependency setup. Only the environment build may retry once, and only for classified network/infrastructure failures. Duration telemetry is read under a test-manifest plus dependency digest and PR jobs never publish shared telemetry.

`Review evidence required` consumes only one exact-head adversarial GitHub PR review from an authenticated, non-builder repository collaborator for R3. PR-body prose is not a receipt transport. Review ID, actor, commit, timestamp, URL, and 24-hour TTL come from GitHub; provider/model strings remain reviewer metadata rather than cryptographically authenticated claims. R4-R5 fail closed because no authenticated specialist mapping or signed attestation service is installed.

The workflow emits `Hermes CI required`, `Review evidence required`, and `Merge admission` without write permissions, merge behavior, or branch-protection authority. Label, body, review, draft, and merge-group changes refresh the workflow. Admission refetches live PR state and fails closed on stale heads/bases, an advanced protected base, conflict or unknown mergeability, draft state, current or outstanding changes requested, unresolved or ambiguous review threads, and case-normalized canonical opt-out labels. Merge-group code proof runs against the synthetic head, but review/admission deliberately fail closed until a protected authority supplies complete constituent membership and per-member risk classification; GitHub's `associatedPullRequests` lookup is not treated as complete queue membership. Fork candidates fail before self-hosted execution.

R0-R2 use no CI model, R3 uses one post-green adversarial receipt under policy 2.1.0, and protected R4-R5 work remains blocked for the named specialist. Existing CI remains authoritative until the single cross-repository administration transaction; rollback is a normal revert.
